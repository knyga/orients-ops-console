# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Feature requirements (non-negotiable)

Every feature MUST ship **two** interfaces, not one:

1. A **web-based** representation (the dashboard UI).
2. A **CLI-based** representation that exposes the same data/answers.

The CLI surface is first-class, not an afterthought: we mostly work with Claude Code to get answers, so each feature must be queryable from the command line (e.g. an `npm run` script or a small Node CLI under `scripts/` / `bin/`) without going through the browser. When adding or changing a feature, build/extend both interfaces and keep the shared logic in the pure `lib/` modules so the web page and the CLI consume the same code path.

## Setup

Copy `.env.example` to `.env` and set `VIMEO_TOKEN` (a Vimeo personal access token with read access to the account's videos). Without it, `GET /api/vimeo` returns 500 and no videos load.

For Google Drive sync, set `GOOGLE_SERVICE_ACCOUNT_KEY` (base64 of a service-account JSON key with Drive read access) and share each Drive file (or a folder) with the service-account email.

Needs `JIRA_*` env; the default project is hardcoded to `ATP` (override with `JIRA_DEFAULT_PROJECT`) and the Mr Lab accountId is hardcoded too — no extra env var needed. Deterministic (no LLM); the conversational agent (Phase B) reuses the same `lib/jira.ts` write client. (Phase A of the Slack conversational agent — see `docs/superpowers/specs/2026-07-01-slack-conversational-agent-design.md`.) - `npm run agent -- "<message>" [--yes]` — the Slack conversational agent's CLI twin (Phase B). Runs the same `lib/agent/loop.ts` multi-turn Claude tool-use loop from the terminal: read tools (`jira_search`) execute live to answer questions (e.g. "what was done in jira today"); a write (`jira_create`/`jira_comment`/`jira_transition`/`jira_update`/`jira_add_to_next_sprint`/`field_loss_set`/`sprint_plan_build`/`field_summary_post`) returns a **confirm-first** Ukrainian proposal that the CLI applies only with `--yes` (`jira_create` shows the resolved Mr-Lab routing; `jira_add_to_next_sprint` names the resolved sprint and whether it will be created; `field_loss_set` and `sprint_plan_build` are approver-only on the **Slack confirm path** — `lib/proposalGate.ts` gates the apply there and injects the approver's name as `by`; the CLI `--yes` is operator-trusted and deliberately ungated (the machine already holds the JIRA/Slack credentials, so a CLI-side identity check would be theatre); `sprint_plan_build` is thread-scoped: it needs `--thread` pointing at the sprint-plan fallback anchor, whose thread the Slack surface supplies automatically). `--thread <channelId:ts | permalink URL>` prepends the live Slack thread's transcript (same `lib/agent/threadContext.ts` the Slack @mention surface uses; needs `SLACK_TOKEN`) so "створи тікет з цього треду" works from the terminal; a thread-born `jira_create` gets the thread's permalink appended to the ticket description **deterministically** (loop `sourceUrl` → `ProposeContext`, clickable via `textToAdf` link marks — the model never relays the URL), on both the CLI and Slack surfaces. Model `claude-sonnet-5`, ≤8 tool iterations / ~50s budget. Needs `ANTHROPIC_API_KEY` + `JIRA_*`. Phase C wires this same loop into Slack (@mention/DM/thread). (See `docs/superpowers/specs/2026-07-01-slack-conversational-agent-design.md`.)
  - **Phase C.2 (confirm-first writes + memory, DM + @mention):** A write request — DM or @mention-in-channel — posts a Ukrainian confirm-first proposal that applies (via the shared `lib/proposalExecutor.applyProposal`) only after the user replies `так`/👍 — the same executor the CLI `--yes` uses. **Mention-only outside DMs (2026-07-07):** a plain thread reply with no re-tagging inside a known agent thread can *only* carry that `так`/`ні` confirm/cancel — any other unmentioned reply is silently ignored (no supersede, the proposal stays pending), and a new request always needs an @mention. All surfaces funnel through one `handleAgentConversation` handler in `app/api/slack/events/route.ts`, keyed by a `conversationKey` (DM → channelId; @mention/thread → thread_ts) that is also the agent-memory key (`agent_threads`, last 10 turns / 24h) and the proposal key. Outside a DM, a pending proposal is confirmed/cancelled by its original requester **or any `lib/approvers.ts` approver** (driver-gating, `canDriveProposal` in `lib/proposalGate.ts`; widened from requester-only 2026-08-31 after an approver's «так» was silently swallowed) — a bystander's plain reply is still silently ignored, but an allowed user's @mention that can't drive the pending proposal gets a visible «⏳ чекаю на підтвердження…» notice instead of silence; the apply-time approver gate for money-affecting kinds now evaluates the confirmer, not the requester. The webhook acks Slack fast and runs the loop in `/api/agent/run` (needs `AGENT_RUN_SECRET`).
  - **In Slack:** DM the bot a question or @mention it in a channel/thread, and it answers via the same loop (read tools — `jira_search` — plus the confirm-first writes above); a plain (unmentioned) reply in an agent thread is only ever a `так`/`ні` on a pending proposal, never a new question. An @mention inside a thread auto-injects the thread's live transcript (capped at 40 messages / ~8k chars, roster-name-resolved — `lib/agent/threadContext.ts`, fetched in `/api/agent/run` via `conversations.replies`) into the turn, so "створи джира тікет з цього треду" uses the whole thread as context; a fetch failure degrades to the bare question, and agent memory stores the original question only. Gated to the two `lib/approvers.ts` approvers only — since 2026-07-08, to prevent misuse; the wider `lib/people.ts` roster is deliberately not enough (anyone else gets a Ukrainian refusal). Handled in `app/api/slack/events/route.ts` (`mention`/`dm`/plain-thread-reply branches → `handleAgentConversation`), deduped by `event_id`. The plain-thread-reply branch (`!hasLeadingMention` + `agentThreadExists`) runs before the tracked-channel filter, since an agent thread can live in any channel, but is confirm/cancel-only (see the mention-only rule above; `docs/superpowers/specs/2026-07-07-agent-mention-only-outside-dm-design.md`); a message that leads with an `@mention` token is left to the mention branch to avoid double-processing. An answer/echo longer than Slack's `msg_too_long` cap (~4000 UTF-8 **bytes**, i.e. ~2000 Cyrillic chars — hit 2026-08-01 by long Jira lists) is delivered **chunked** (`lib/slackChunk.ts`, pure + tested): the placeholder edit carries the first chunk, the rest follow as separate posts (threaded outside DMs, top-level in a DM) — never one oversized send. The web Assistant tab is a separate C.2 surface. Operator prerequisite: subscribe the Slack app to `app_mention` + `message.im` events and add scopes `app_mentions:read`, `im:history`, `im:read`, `im:write` (plus the existing `chat:write`; a channel agent thread also needs the bot invited to that channel). (See `docs/superpowers/plans/2026-07-02-slack-agent-phase-c1-ingress.md` and `docs/superpowers/specs/2026-07-02-slack-agent-phase-c2-writes-design.md`.)
- `npm run slack-link -- <permalink> [<permalink> …] [--format json]` — resolve a Slack message permalink (`https://<ws>.slack.com/archives/<CHANNEL>/p<16 digits>[?thread_ts=…]`) into readable text: the message with author (roster name) + Kyiv time, or — when it is a thread parent with replies or a reply — the WHOLE thread oldest-first with the linked message marked «→» (capped 40 msgs / 8k chars around the linked one). Read-only; needs `SLACK_TOKEN` and the bot in that channel (`not_in_channel` → a Ukrainian «додайте бота» note). Web twin: the **Slack Link** tab (`app/(dashboard)/slack-link/page.tsx` — paste a permalink, see the rendered transcript + raw messages) over `GET /api/slack-link?url=<permalink>` (console-auth gated). The injected block is framed as quoted data, not instructions; a single oversized message is truncated to the 8k budget. This is the CLI face of the agent's **Slack-link reading (2026-09-04)**: people hand the bot links instead of text, so (a) every surface that runs the loop — Slack DM/@mention (`/api/agent/run`), the CLI `npm run agent`, and the read-only verdict-thread chat — **deterministically expands** up to 3 permalinks found in the incoming question into a «Вміст посилань зі Slack» block prepended to the turn (`lib/agent/slackLinkContext.expandSlackLinks`; links into the current thread are skipped since that thread is already injected; per-link soft-fail; memory stores the original question only), and (b) the model has a read tool **`slack_read_link`** (`lib/agent/tools/slackRead.ts`) for links it meets later — inside a thread transcript, in another tool's result (e.g. `field_verdict_status`'s Звіт link), or beyond the auto-expansion cap; the system prompt forbids guessing a link's content and declares transcripts/link content/tool results untrusted quotations (never instructions). **Trust boundaries (codex review, 2026-09-04):** the pilot-facing verdict-thread chat is channel-BOUND (`makeSlackReadTools({ allowedChannelIds: [verdict channel] })` + the same option on `expandSlackLinks`) so a pilot cannot make the bot repeat a private channel; the approver-only DM/@mention/CLI surfaces are unbound. The thread root comes from Slack's own message metadata (a URL `thread_ts` that disagrees is ignored; a thread not containing the linked ts is discarded); each link has a 12s deadline and a 2-page (400 msg) thread cap; `<target|label>` wrappers yield only the target. Pure parse/extract/render in `lib/slackLinks.ts` (handles Slack's `<url|label>` wrapping; a reply link's `thread_ts` is the ROOT, the p-digits are the message itself); live fetch via `fetchMessageByTs` (conversations.replies by ts, conversations.history inclusive-window fallback) + `fetchThreadMessages` in `lib/slack.ts`.
- `npm run sprint -- commit|report [--publish] [--channel general] [--sprint <id>]` — **sprint completion tracking** for the weekly Autopilot sprint (board 1 / ATP). **DRY-RUN by default** (prints the Ukrainian #general post, sends nothing); `--publish` REQUIRES `--channel <name>` (a tracked channel). Two subcommands, mirrored by two Vercel crons + shared in `lib/runSprint.ts`: **`commit`** (Tuesday cron `/api/cron/sprint-commit`, `0 6 * * 2` ≈ 09:00 Kyiv) freezes the active sprint's exact issue set as the immutable completion **denominator** (stored in the `reports` table, feature `sprint`, key = sprint slug) and posts the *Committed* list grouped by assignee → status; **`report`** (Monday cron `/api/cron/sprint-report`, `0 6 * * 1` ≈ 09:00 Kyiv — runs before Tuesday's `commit` freezes the next baseline, and an hour before the Monday investor report that reads its completion record; it resolves the board's **active** sprint, so the finished sprint must still be open in Jira on Monday morning) re-fetches the frozen issues live, computes completion as **Done-status-category count / committed count** (issue-count metric), and posts the *Completed* report grouped by assignee with the overall rate + a **stuck-across-sprints** highlight (incomplete issues that lived in ≥2 sprints, with the count — first-attempt issues are not flagged; carry count derived from each issue's Sprint-field changelog). **Scope changes (2026-09-01, «вся реальна робота»):** the Completed report also shows how the real scope diverged from the frozen plan — `➕ Додано після коміту` (live membership minus frozen, with done count), `➖ Знято зі спринту` (frozen keys gone from the live membership, live status shown) and `🔧 Виконано поза спринтом` (issues resolved in the sprint's Kyiv window that never touched the sprint) — one anchor line per non-empty group + per-assignee thread blocks, persisted as `completed.scope` and rendered on the Sprint web tab; the headline % keeps the frozen denominator (visibility, never the metric). The added/removed diff is computed only while the sprint is still **active** — closing a sprint strips incomplete issues' association (observed: 31/45 vanished from `sprint = <id>` after close), so a closed sprint keeps only the unplanned axis; the whole scope stage soft-fails (a Jira error never blocks the post). An explicit `--sprint <id>` now also matches closed sprints, so a late report can run after rollover. No frozen baseline → `report` skips (can't measure). **No active sprint → fallback anchor (2026-08-26):** `commit` no longer fails invisibly in the rollover gap (prev sprint closed, next not started — bit ATP 46/48): with `--publish` it posts a Ukrainian fallback anchor («📋 План спринту не складено…», `formatNoSprintAnchor`) keyed `sprint-plan-pending:<channel>:<Kyiv day>` (a ±59-min re-fire dedups; a missed next week reposts), and the dry-run prints that exact text; once the sprint exists an approver @mentions the bot in the anchor's thread («склади план спринту») → the agent's confirm-first **`sprint_plan_build`** write tool proposes with a live issue count, and on «так» the executor (`lib/proposalExecutor.ts`) freezes the baseline via `runSprintCommit`, **rewrites the anchor in place** into the real Committed post (edit key `sprint-plan-filled:<channel>:<slug>`, namespaced apart from the post reservation) and threads the details under it — guarded by `findSentByTs(anchorTs)` so only a real pending anchor can be rewritten (a same-sprint re-apply is the retry path; an anchor already filled with a *different* sprint refuses), the edit claims the committed anchor key via `claimSentKey` so a later cron re-fire dedups instead of posting an orphan duplicate, and approver-gated in `lib/proposalGate.ts` on the Slack confirm path (the CLI twin — `npm run agent -- "склади план спринту" --thread <channelId:ts> --yes` — is operator-trusted and ungated). `report`'s no-active-sprint/no-baseline skips are unchanged. **Anchor + thread (2026-08-26):** each subcommand posts ONE short #general anchor (headline count/rate + one line per assignee + a stuck COUNT) and puts the per-issue detail in that anchor's THREAD, one reply per packed ≤3800-byte chunk (`buildCommittedPost`/`buildCompletedPost` → `{anchor, details[]}`; a section that spills repeats its header as «_(продовження)_», and an anchor that would blow the cap sheds its per-assignee roster into the first thread message instead). Before this, a >4000-char post was **silently split by Slack itself** into two channel messages from one send, and the recorded `outbound_messages.ts` pointed at the tail. Idempotency: keys are `sprint-<kind>:v2:<channel>:<slug>` for the anchor + `:t<N>` per reply (channel-scoped so a test-channel publish can't hand the #general run a foreign `thread_ts`; `v2` keeps the old single-post keys from colliding), and the exact texts are **frozen** in the sprint record (`published[]`, `lib/sprintPublish.ts`) on the first publish and replayed verbatim on a retry — otherwise a retry that re-fetches Jira repacks different text into the same positional keys and drops or duplicates the issues on a chunk boundary. A send the chokepoint skips with no ts (stuck `pending` row — `decideReserve` only reclaims `failed`) now **throws** instead of silently losing that chunk. Pure logic + tests in `lib/sprintReport.ts` + `lib/sprintPublish.ts` (orchestration in `lib/runSprint.test.ts`); Jira fetchers `fetchSprintIssues`/`fetchIssuesByKeys` in `lib/jira.ts`; store in `lib/sprintStore.ts`. Backs the **Sprint** web tab (`GET /api/sprint`). Needs `JIRA_*` (+ `JIRA_BOARD_ID`, default 1), `CRON_SECRET` for the crons, `chat:write` to post. (See `docs/superpowers/specs/2026-07-19-sprint-completion-design.md`.)

## Architecture

An internal ops console (Next.js 16 App Router, React 19, Tailwind v4, TypeScript strict). Shipped features: **Field Ops video reconciliation**, **Dev Reporting (Jira)**, and **GitHub Activity** — the dashboard nav is data-driven with an `enabled` flag (`app/(dashboard)/layout.tsx`).

### Artifacts & the skill→CLI→committed-artifact→web pattern (read this for any new feature)

**Claude Code is first-class: the skill/CLI is the product.** Each reporting feature's CLI (`npm run <feature>`) computes a period's data and, with `--write`, persists **two committed sidecars** under `reports/<feature>/<period>.{json,csv}`: a **lossless JSON** (the web's render source — the exact shape `GET /api/<feature>` returns) and a **flat CSV** (a human/spreadsheet record; intentionally lossy — no nested data like sprint churn or repo ranking). The shared read/write/list logic is in `lib/reports.ts` (CLI-safe, **not** `server-only`); the pure period-key helpers are in `lib/period.ts` (client-bundle-safe, no `node:fs`). `periodKey` is the canonical key: `YYYY-MM` for a single month, else `YYYY-MM-DD_YYYY-MM-DD`.

The web is **hybrid**: `GET /api/<feature>` serves the committed JSON for `?period=<key>` (404 when absent), lists committed periods for `?periods=1`, and falls back to a **live** fetch for `?refresh=1&start=&end=` (the only network path). **The web never writes `reports/` — committing artifacts is exclusively the CLI's job.** The reporting pages share the `lib/usePeriodReport` hook (period picker → render newest committed → "Refresh live" for the current month). Field Ops is the exception: `/api/field-ops` is committed-only because live reconciliation needs the ephemeral pasted flight hours, which stays a client computation against `/api/vimeo?refresh=1`.

To add a new reporting feature, follow `.claude/skills/authoring-reporting-features/SKILL.md`.

### The reconciliation domain (read `lib/reconcile.ts` first)

The business policy lives as a doc comment at the top of `lib/reconcile.ts` and drives the whole app. Key invariants:

- Video is **not** paid per-minute. Recording completeness **gates** the daily field bonus: a flight day passes (`OK`) only when recorded Vimeo minutes ≥ **50%** (`MIN_RATIO`) of flight minutes. Comparison is `>=`, so an exact 50% match passes.
- Below 50%, or any video-without-flight / zero-hour day, is `FLAG` — meaning "needs a human decision", **never** an auto-reject (force-majeure/tech-failure exceptions exist).
- Days are grouped by video **upload date** (`created_time`), not flight date, because uploads can lag up to a working day. Day boundaries use `FIELD_TIMEZONE` (`Europe/Kyiv`), not UTC — see `videoUploadDate`.

`lib/reconcile.ts` and `lib/flightHours.ts` are **pure** (no React/Next imports) and unit-tested — keep them that way. `reconcile.ts` exposes `aggregateByDay` (videos + flight days → daily rows) and `summarize` (daily rows → period totals + flagged days).

### Server/client boundary (the Vimeo token must never reach the browser)

- `lib/vimeo.ts` imports `server-only` and reads `process.env.VIMEO_TOKEN`. The `server-only` import makes an accidental client import a build error — do not remove it, and do not import this module from a `"use client"` file.
- The browser calls `app/api/vimeo/route.ts` (`GET /api/vimeo?start=&end=`), never Vimeo directly. The route validates `YYYY-MM-DD` bounds and maps `VimeoError` → 502 (upstream) or 500 (missing config/token).
- `fetchVideosInPeriod` relies on Vimeo's `sort=date&direction=desc` to stop paging early once a page predates `start`, so it never scans full account history. All Vimeo fetches use `cache: "no-store"` — reconciliation must reflect live truth.

The same server-only client also backs a CLI, `scripts/vimeo.ts` (run via `npm run vimeo`). Because `lib/vimeo.ts` imports `server-only` — whose default export throws — the CLI runs Node with `--conditions=react-server` so that import resolves to its empty module. All shaping lives in the pure, tested `scripts/vimeoStats.ts`. The same `server-only` + `--conditions=react-server` discipline applies to `lib/jira.ts`, `lib/github.ts` (token-injected client in `lib/githubClient.ts`, which is deliberately *not* server-only) and `lib/summarize.ts`. Reconciliation now also has a CLI — `npm run fieldops` (`scripts/fieldops.ts`) — combining live Vimeo with committed flight hours.

### UI flow

`app/(dashboard)/field-ops/page.tsx` defaults to rendering the **committed** reconciliation for the selected period (read-only). Its **Live (unsaved)** mode is the original interactive flow: fetch videos via `/api/vimeo?refresh=1`, paste flight hours into `FlightHoursEditor` (CSV parsed by `lib/flightHours.ts`, tolerant of headers/blank lines/`,` or `;`), reconciliation recomputed client-side in a `useMemo` calling `aggregateByDay`/`summarize`. Pasted flight hours are still **ephemeral**; to make a month a committed source of record, the hours are committed to `reports/field-ops/inputs/<period>.csv` and `npm run fieldops -- --write` produces the artifact. The Dev Reporting and GitHub pages follow the shared `usePeriodReport` hybrid pattern (committed by default, live Refresh for the current month).
